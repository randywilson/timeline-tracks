# Timeline Tracks — iOS

iOS port of the Android app at `../app/`. Same purpose: request GPS fixes at a user-set interval, keeping the device's location hardware active so that location-aware apps (Google Timeline, etc.) receive timely, accurate fixes. No data stored, no internet permission, GPL-3.0.

## Project structure

```
ios/
  TimelineTracks/
    TimelineTracksApp.swift      App entry point
    ContentView.swift            SwiftUI UI (interval, toggle, start/stop, stats, permission warning)
    LocationTracker.swift        CLLocationManager wrapper, permission flow, rate-limiting, auto-stop
    AutoStopChecker.swift        Deque-of-4 stationary detection (ported from Android)
    Prefs.swift                  UserDefaults wrapper (mirrors ../timeline-tracks/.../Prefs.java)
    Info.plist                   Background modes, location usage descriptions
    PrivacyInfo.xcprivacy        Required privacy manifest (no data collected)
  TimelineTracks.xcodeproj/
```

Shared assets in `../store/` (icons, store descriptions, localized strings).

## Implementation sketch

The app is small — ~5 source files plus config:

1. **`TimelineTracksApp.swift`** — App entry point (auto-generated by Xcode, minimal changes needed).
2. **`ContentView.swift`** — SwiftUI view: interval field, auto-stop toggle, mode picker ("Reliable" / "Battery Saver"), start/stop button (green/red), stats text, permission warning banner, info dialogs. Roughly mirrors `activity_main.xml` + parts of `MainActivity.java`.
3. **`LocationTracker.swift`** — `ObservableObject` class wrapping `CLLocationManager`. Handles the two-step permission flow, starts/stops updates, implements both `TrackingMode` behaviors (continuous rate-limiting vs. periodic timer+burst), feeds accepted fixes into `AutoStopChecker`. Replaces `LocationService.java`. No separate background service class is needed — `CLLocationManager` with `allowsBackgroundLocationUpdates = true` handles background execution directly.
4. **`AutoStopChecker.swift`** — Direct Swift port of the deque-of-4-locations stationary detection from `LocationService.java`. Pure algorithm, no platform dependency.
5. **`Prefs.swift`** — `UserDefaults` wrapper. Direct port of `Prefs.java`.
6. **`Info.plist`** additions: `UIBackgroundModes = [location]`, `NSLocationWhenInUseUsageDescription`, `NSLocationAlwaysAndWhenInUseUsageDescription`, `NSLocationAlwaysUsageDescription`.
7. **`PrivacyInfo.xcprivacy`** — Required since Spring 2024. Declares no data collected, no tracking, no third-party SDKs.

## Language and UI framework

**Swift + SwiftUI.** SwiftUI is declarative — you describe what the UI looks like for a given state; the framework handles rendering. Conceptually similar to XML layouts but expressed in code. `@StateObject` / `@ObservedObject` drive UI updates from `LocationTracker`.

## Platform API mapping

### Location

iOS has no equivalent to Android's interval-based GPS wakeup (`requestLocationUpdates(GPS_PROVIDER, intervalMs, ...)`). On Android the OS cycles the GPS chip and lets it sleep between fixes; on iOS there is no API to instruct the OS to do this. The app therefore offers two tracking modes:

```swift
enum TrackingMode {
    case continuous  // always-on GPS; chip never sleeps
    case periodic    // low-accuracy idle + periodic GPS burst
}
```

**`continuous` mode ("Reliable" in UI)**

`startUpdatingLocation()` with `desiredAccuracy = kCLLocationAccuracyBest` and `distanceFilter = kCLDistanceFilterNone`. The GPS chip runs at all times while tracking. In `locationManager(_:didUpdateLocations:)`, record the time of the last accepted fix and ignore newer ones until `intervalSecs` has elapsed. Battery use is similar to a navigation app like Strava.

**`periodic` mode ("Battery Saver" in UI)**

Run `CLLocationManager` continuously at `desiredAccuracy = kCLLocationAccuracyThreeKilometers` (uses cell/WiFi positioning — very low drain). This idle connection also keeps the app's RunLoop alive in the background, allowing a `Timer` to fire reliably. Every `intervalSecs`, the timer sets `desiredAccuracy = kCLLocationAccuracyBest`; when a fix arrives with `horizontalAccuracy <= 20` metres, or after a 20-second timeout, drop back to `kCLLocationAccuracyThreeKilometers`.

Caveats for `periodic` mode (document these in the UI's info text and App Store listing):
- Whether the accuracy change actually triggers the GPS chip is undocumented behavior in Core Location. `locationd` may return a cached high-accuracy fix instead.
- Cold GPS acquisition can take 5–30 seconds; if no fix arrives within the timeout, the burst ends with whatever cell/WiFi fix is available.
- Other apps (Google Timeline) only benefit if they have an active `CLLocationManager` request at the moment the burst fires — iOS has no equivalent to Android's FLP cache that stores fixes for later delivery.
- Battery use is meaningfully lower than `continuous` (~15–25% GPS duty cycle at a 2-minute interval) but not zero — the idle cell/WiFi session has a small ongoing cost.

| Android | iOS (`continuous`) | iOS (`periodic`) |
|---|---|---|
| `GPS_PROVIDER` with interval | `kCLLocationAccuracyBest`, always-on | `kCLLocationAccuracyThreeKilometers` idle + timed burst to `kCLLocationAccuracyBest` |
| Chip sleeps between fixes | No | Approximately — not guaranteed |
| Reliable fix at each interval | Yes | Best-effort |

### How GPS sharing works on iOS (vs Android)

On Android, `GPS_PROVIDER` feeds the platform's Fused Location Provider cache — all apps receive your fixes directly. iOS does not share `CLLocationManager` fixes between apps.

However, Core Location is a shared hardware layer. When this app holds an active `CLLocationManager` with `kCLLocationAccuracyBest`, the GPS chip stays powered. Other apps that also request location (Google Maps, Google Timeline) receive timely hardware-fresh fixes because the chip is already running. The net effect is the same as Android; the mechanism is indirect rather than direct. Describe it accurately in the App Store listing.

### Background execution

- **`Info.plist`**: `UIBackgroundModes = [location]`
- **`CLLocationManager`**: `allowsBackgroundLocationUpdates = true`, `pausesLocationUpdatesAutomatically = false`

With these set, the app continues receiving location callbacks while backgrounded and the screen is off. The OS shows a blue status-bar indicator (or location pill on newer iPhones) while background location is active. No persistent notification is needed while running — the indicator is sufficient. Show a local notification when tracking auto-stops so the user knows.

### Permissions (two-step — not skippable)

1. First: `requestWhenInUseAuthorization()` → "Allow While Using App"
2. After granted: `requestAlwaysAuthorization()` → "Always Allow" (separate native dialog)

Both must be granted for background operation. Also check `CLLocationManager.accuracyAuthorization` (iOS 14+): if `.reducedAccuracy`, show a message asking the user to enable precise location — the auto-stop distance math requires real GPS coordinates.

### Preferences

`UserDefaults` is the iOS equivalent of Android's `SharedPreferences`. Same concept, slightly simpler API.

```swift
// Prefs.swift mirrors Prefs.java
// Keys: intervalSeconds (Int, default 110), autoStop (Bool, default true),
//       trackingMode (String, "continuous"|"periodic", default "continuous"),
//       running (Bool), startTime (Double), stopTime (Double),
//       locationCount (Int), stopReason (String, "stopped"|"auto-stopped")
```

### Auto-stop

Direct Swift port of Android's deque logic: maintain a rolling deque of 4 recent `CLLocation` values. When a new fix arrives, if `newFix.distance(from: each) <= 100` for all 4 deque entries (5 total points within 100 m), stop tracking. `CLLocation.distance(from:)` is the iOS equivalent of Android's `Location.distanceTo()`.

### No battery optimization bypass

iOS has no equivalent to Android's `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`. The `allowsBackgroundLocationUpdates = true` + `pausesLocationUpdatesAutomatically = false` combo is the maximum available. The OS may still pause delivery in Low Power Mode; document this limitation in the app description.

## App Store productionization notes

**Apple Developer Program**: $99/year required to submit. Free provisioning lets you run on your own device during development.

**Background location review scrutiny**: Apps with `UIBackgroundModes: [location]` get extra App Review scrutiny. Prepare a clear reviewer note: "This app requests GPS fixes at a user-set interval to keep the device location hardware active, improving accuracy for Google Timeline and other navigation apps. It collects and stores no data." First submission may be rejected; one round of clarification is typical.

**Privacy Manifest** (`PrivacyInfo.xcprivacy`): Required since May 2024. For this app: no data collected, no tracking, no third-party SDKs. Straightforward, but must be present or the upload is auto-rejected.

**Signing**: Use Xcode automatic signing for development. For CI/CD, use `fastlane match` to manage certificates in a private git repo.

**TestFlight path**: Archive → upload to App Store Connect → internal testers (you) can install immediately → external Beta Review (usually same-day) → App Store submission (24-72 hours first time).

## Workflow rules

- **Translations**: When English strings change, update all locale-specific `Localizable.strings` files under `ios/TimelineTracks/<locale>.lproj/` before committing. Locales to maintain: en, de, fr, es, pt-BR, ja, ko, zh-TW, hi, it, id (mirrors Android store locales).
- **Tests**: Unit-test `AutoStopChecker` and `Prefs` equivalents (XCTest). Test background location behavior on a real device — Simulator background mode is unreliable.
- **Background smoke test**: Start tracking, lock screen, wait 5+ minutes, unlock — confirm location count incremented. This is the core functional requirement and cannot be verified in Simulator.
